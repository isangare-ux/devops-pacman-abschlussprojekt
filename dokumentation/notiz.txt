3. Analyse Docker-Lösung

alte Docker Lösung ist nicht zu übernehmen, Da Image (node:boron) aus Sicherheitgründe und Wartbakeit  unpragmatisch s
Container Start, stop, sind manuell. Container sind nicht reproduzierbar und schlecht skalierbar.
Volume Erstellung ist für lokale Entwicklung geeignet aber nicht Kubernetes Produktion, da Komponente Erstellung dynamisch, skalierbar und dinamische sind.
Es entpricht devops Norme nicht mehr wie GitOp, Kubernetes Einsatz nicht möglich.
Image ist nur Online verfügbar es besteht der Risiko, dass Image veraltet oder nicht verfügbar ist.

4. Anforderungen neue Lösung
mit alten Docker Version wird die Build manuell erstellt, dafür soll Entwickler viele tippen. 
Die Lösung ist dieser Prozess mit GitHub zu automatisieren dh. Build werden automatisert erstellt und zur verfügung gestellt.
Früher waren die alte Image local gespeichert, wenn man gut SW-Stand haben möchte, sollte man continuerlich verbessert bzw. integriert werden.
Dafür ist eine Versionierung mit GHCR bessere Lösungsweg. Docker run Befehl immer einzutippen ist ungüstig, da falls ein 
Container kapput gehen sollte muss der Anwender immer entsprechen Fehler detektieren falls nötig ist Container neue starten und neue erstellen.
Aus diesem Grund in Kubernestes sehr Interessant, das Tool gibt uns die Möglichkeit Node zu skalieren, Max Pod die am 
laufen gebracht werden muss dran zu halten. Falls ein Pod kapput wird der erwarte Anzahl von Pod sorfort zur Verfügung gestellt also die Skalierung
ist eine der Hauptgrund Vorteile bzw. Faktor.

Mit alten Docker bzw. Infrakstruktur war die sync von Kubernets ´über deployment nicht möglich. Mit aktuell DevOps Architektur
sind Argo CD GitOps unversichbar, Argo cd gibt die Möglichkeit Image zu verwaltet, versionieren, veroffentlich und wird von 
ci/cd als Info Quelle verwendet.

Prometheus/Grafana gibt mit die Möglichkeit mit akuellen devOps Stand zu halten
Prometheus sammelt Info via cpu Auslastung, Ram, Anzahl von Pods, Verfügbarkeit von Anwendung, Antwortzeiten und Grafana
liest Info aus Prometheus und stellt die Info grafisch dar. Dadurch werde die Probleme schnell erkannt

5. Fazit

Nach alte Docker Analyse wurde festgestellt, dass bestehende Docker Containerfähig ist. 
Aber es fehlt Grundsätlich  Aktuell DevOps Stand dh. Container Image ist nicht auf aktuell stand, In der Regel soll 
man imme mit neue Image arbeiten, die Anwendung betreibt und Anwendung soll immer versionierbar sein.
CI/CD ist heute zu Tag normal um diese neue Archithek zu arbeiten, ist erforderlihc mit GitHub, Container Registry, 
pacman-gitops, Argo cd, Kubernetes Cluster Tool zu arbeiten, die Anwendung reproduzierbar, versionierung und 
wieder verwendbar zu machen.
